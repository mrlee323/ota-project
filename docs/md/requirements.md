## 0. 용어

| 용어 | 뜻 |
|---|---|
| **MD** | 기획전 페이지. 「PHR 브랜드 위크」처럼 목적을 갖고 한시적으로 여는 한 장짜리 페이지 |
| **모듈** | MD 를 이루는 블록 한 종. 정의(필드 목록) + 렌더 컴포넌트 한 쌍 |
| **템플릿** | 모듈을 미리 배열해 둔 시작점. 빈 캔버스 대신 이걸로 시작한다 |

| **페이지 JSON** | MD 한 건의 저장 형태. 모듈 배열 |
| **팬아웃** | MD 하나에서 파생되는 부산물(OG 이미지, 썸네일 등) |

> **`showcase` 와 무관하다.** 기존 `RegionShowcaseData` / `showcase_contents` 는 메인 화면의 지역 특가 구좌이고,
> MD 는 별도 도메인·별도 테이블·별도 공개 라우트다. 재사용하는 것은 호텔 카드의 **표시 규칙**뿐이다.

## 1. 문제

실사 결과([module-survey.md](./module-survey.md) F1) — 공개 기획전의 **약 90%가 디자이너가 자른 이미지**다.

여기서 세 가지가 따라온다.

| 문제 | 근거 |
|---|---|
| 페이지 한 건에 디자이너가 반드시 붙는다 | 이미지가 없으면 페이지가 성립하지 않는다 |
| 가격·문구 한 줄 고치는 데 이미지를 다시 만든다 | 가격이 이미지 안에 그려져 있다 (F5) |
| 페이지 내용이 검색·복사되지 않는다 | 호텔 이름조차 `img[alt]` 로만 존재 (F1) |

**진단** — 도구가 없는 게 아니라 **조립할 블록이 없다.**
그래서 이 프로젝트의 산출물은 UI 가 아니라 **모듈 정의(스키마) 층**이다.

## 1.5 자동화의 세 층 — 어디를 자동화하는가

「자동화」는 한 덩어리가 아니다. 세 층으로 나눠야 범위가 흐려지지 않는다.

| 층 | 무엇을 자동화하나 | 이 프로젝트에서 |
|---|---|---|
| **① 조립** | 사람이 만들되 **개발·디자인을 안 거치게** — 블록을 추가한다 | **범위 안 (본편)** · FR-1~4, 6 |
| **② 소싱** | 어떤 호텔을 넣을지 조건으로 자동 선정 | **범위 밖** — 상품 데이터가 mock 이라 판단 근거가 없다 |
| **③ 생성** | 이미지·카피를 AI 가 만든다 | **부분** — 카피/구성만(FR-5). **이미지 생성은 안 한다** |

②를 빼는 이유를 분명히 해 둔다 — 소싱은 «어떤 호텔이 잘 팔리나» 를 아는 문제고,
그건 조립 도구가 아니라 데이터의 문제다. 조립이 되기 전에 손대면 둘 다 못 끝낸다.

③에서 이미지 생성을 뺀 이유는 §2 비목표에 있다.

## 2. 목표 / 비목표

### 목표

| # | 목표 | 판정 |
|---|---|---|
| G1 | 디자이너 이미지 없이 MD 한 건을 만들 수 있다 | 템플릿 4종 중 T3 를 이미지 0장으로 완성 |
| G2 | 실제 기획전을 모듈 조합으로 재현할 수 있다 | 실사 표본 7건 중 **3건 구조 재현** (§6 AC-1) |
| G3 | 모듈을 늘리는 비용이 일정하다 | 모듈 1종 추가 = **수정 2곳** |
| G4 | 요청서 한 장으로 초안이 나온다 | 요청서 → 페이지 JSON, 스키마 1차 통과율 ≥ 70% (L1) |
| G5 | 가격·할인율이 데이터라 저절로 맞는다 | `hotel-card-list` 가 값으로 렌더 |

### 비목표 (이번에 안 한다)

- 픽셀 단위 재현 — G2 는 **구조** 재현이지 시각 복제가 아니다
- 디자인 자유도(자유 배치·자유 폰트) — 모듈이 허용하는 범위 안에서만
- 다국어 / A/B 테스트 / 예약 발행 / 버전 히스토리
- **문맥 없는** 이미지 생성 — 「이미지 만들어줘」식 자유 생성. **문맥을 주입한 생성은 범위 안**이다 ([mcp.md §5](./mcp.md)): 슬롯·디자인 토큰·인접 모듈 값을 서버가 붙이고, 이미지에 텍스트·얼굴·실제 건물을 넣지 않는다
- 앱(WebView) 대응 — 웹 반응형까지

## 3. 사용자

개인 프로젝트라 실사용자가 없다. **그래서 더 명시적으로 정한다** — 아래 세 역할이 요구사항의 판정 기준이다.

| 역할 | 하는 일 | 이 사람이 못 하면 실패인 것 |
|---|---|---|
| **운영 담당자** (주 사용자) | 템플릿 고르고 값 채워 발행 | 개발자 도움 없이 MD 를 발행한다 |
| **디자이너** | 모듈 자체의 모양을 정한다. 개별 MD 는 손대지 않는다 | 모듈을 고치면 이미 발행된 MD 가 같이 좋아진다 |
| **개발자** (나) | 모듈을 추가한다 | 모듈 1종 추가에 파일 2개보다 많이 안 고친다 |

**최종 사용자(여행자)** 는 발행된 MD 를 본다 — 요구사항은 성능·접근성(NFR)으로 걸린다.

## 4. 범위

```
                         ┌─────────────────┐
   자연어 요청  ────────▶ │  LLM 조립 (FR-5) │ ──┐
                         └─────────────────┘   │
                                                ▼
   템플릿 선택  ─────────────────────────▶  페이지 JSON  ──▶  캔버스 편집 (FR-3)
                                                │
                                                ▼
                                          발행 (FR-4)
                                                │
                              ┌─────────────────┴──────────────┐
                              ▼                                ▼
                     공개 MD 페이지 (FR-6)              OG 이미지 (FR-7)
```

**범위 안** — 모듈 정의·렌더러·캔버스·템플릿·LLM 조립·공개 페이지·OG
**범위 밖** — 호텔 상품 데이터 수집, 결제·예약, 마케팅 채널 발송, 통계

## 5. 기능 요구사항

### FR-1 모듈 정의

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-1.1 | 모듈은 **정의(필드 목록) + 렌더 컴포넌트** 한 쌍으로 존재한다. 정의는 데이터다 | 必 |
| FR-1.2 | v1 모듈 6종: `hero` `image` `section-title` `hotel-card-list` `notes` `cta` | 必 |
| FR-1.3 | 모듈 1종 추가에 고치는 파일은 **2개를 넘지 않는다** (정의 등록 · 컴포넌트 등록) | 必 |
| FR-1.4 | 각 모듈은 **샘플 값**을 갖는다. 캔버스에 올리면 빈 껍데기가 아니라 예시가 보인다 | 必 |
| FR-1.5 | 각 필드는 LLM 이 읽을 **설명문**을 갖는다. 프롬프트에 모듈 설명을 따로 쓰지 않는다 | 必 |
| FR-1.8 | 각 모듈은 **`whenToUse`**(언제 쓰는 모듈인가)를 갖는다. 모듈이 100개가 되면 «이게 뭔가»(description)로는 못 고른다 → [mcp.md §4](./mcp.md) | 必 |
| FR-1.6 | v2 모듈: `feature-carousel` `coupon` | 有 |
| FR-1.7 | 각 필드는 **자유도 등급**을 갖는다 — `fixed`(못 고침) / `preset`(정해진 값 중 선택) / `free`(자유 입력). `free` 는 예외적으로만 준다 | 必 |

### FR-2 페이지 데이터

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-2.1 | MD 는 **모듈 배열 JSON** 으로 저장한다. HTML 로 저장하지 않는다 | 必 |
| FR-2.2 | 모듈 마크업을 고치면 **이미 저장된 MD 도 같이 바뀐다** | 必 |
| FR-2.3 | 색은 값이 아니라 **토큰 이름**으로 저장한다. 예외는 구간 배경색 1종 | 必 |
| FR-2.4 | 렌더러가 모르는 모듈 타입은 **건너뛴다. 던지지 않는다** | 必 |
| FR-2.5 | 저장 시 모듈 정의로 값을 검증한다. 실패하면 저장 대신 오류를 보여준다 | 必 |
| FR-2.6 | 필드 이름 변경은 금지, 추가만 허용한다 (additive-only) | 必 |

### FR-3 캔버스 (어드민)

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-3.1 | 팔레트에서 모듈을 골라 페이지에 얹는다 | 必 |
| FR-3.2 | 모듈 순서를 바꾸고 삭제할 수 있다 | 必 |

| FR-3.4 | 편집 결과가 실제 렌더러로 즉시 보인다. 별도 미리보기 UI 를 만들지 않는다 | 必 |
| FR-3.5 | 템플릿 4종 중 하나를 골라 시작할 수 있다 | 必 |
| FR-3.6 | 반복 묶음(호텔 1곳 = 3~4블록)을 **한 단위로** 추가할 수 있다 — 블록의 `group` 태그로 인식 | 必 |

### FR-4 상태·권한

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-4.1 | 상태는 `draft` → `published` → `archived`. 되돌리기 가능 | 必 |
| FR-4.2 | `published` 만 공개 URL 에서 보인다. `draft` 는 미리보기 링크로만 | 必 |

### FR-5 L1 — 요청서 → MD

정형 요청서에서 **값을 뽑아** 템플릿에 꽂는다. 페이지 구성은 템플릿이 이미 정한다.

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-5.1 | 요청서(정형 폼)에서 템플릿이 요구하는 필드 값을 추출한다 | 必 |
| FR-5.2 | 추출 스키마는 **모듈 정의에서 만든다.** 모듈이 늘면 프롬프트가 저절로 따라온다 → [llm.md §2](./llm.md) | 必 |
| FR-5.3 | 결과를 스키마로 검증한다. 실패하면 오류를 붙여 **재요청 1회** | 必 |
| FR-5.4 | 재요청도 실패하면 뽑힌 값만 넣어 `draft` 로 저장한다. **버리지 않는다** | 必 |
| FR-5.5 | **호텔을 지어내지 않는다.** 카드 값은 실제 호텔 데이터에서만 채운다 | 必 |
| FR-5.6 | 생성 결과는 항상 `draft` 다. 자동 발행하지 않는다 | 必 |
| FR-5.7 | 공급자를 코드에 박지 않는다 — **OpenAI 호환 `baseURL` 교체**로 갈아끼운다 ([llm.md §2](./llm.md)) | 必 |
| FR-5.9 | 이미지 생성 배관은 기존 `showcaseAiService` 것을 재사용한다. 새로 만들지 않는다 | 必 |
| FR-5.8 | 빈 `image` 모듈을 문맥 기반으로 채울 수 있다 (§FR-7.3 제약을 따른다) | 有 |

### FR-6 공개 페이지

| ID | 요구사항 | 우선 |
|---|---|---|

|---|---|---|
| FR-7.1 | 페이지 JSON 의 `hero` 값으로 OG 이미지를 만든다 | 必 |
| FR-7.2 | 썸네일·배너 등 나머지 부산물 | 無 (v2) |


### FR-9 템플릿

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-9.1 | 템플릿은 **DB 에 저장한다.** 모듈 배열 + 이름 + 설명 | 必 |
| FR-9.2 | 기본 템플릿 4종(T1~T4)은 **시스템 템플릿**으로 시드된다 | 必 |
| FR-9.3 | 사용자가 캔버스 구성을 **자기 템플릿으로 저장**할 수 있다 | 必 |
| FR-9.4 | 템플릿 **즐겨찾기** — 목록 상단에 고정 | 必 |
| FR-9.5 | 템플릿은 기본 **개인 소유**. 공유는 «공유하기» 로 명시적 승격 — v1 은 컬럼만 | 有 |
| FR-9.7 | 템플릿은 **한 종류다** — 전체 페이지 골격. 반복 묶음은 별도 엔티티가 아니라 블록 태그로 푼다 (FR-3.6) | 必 |
| FR-9.8 | 즐겨찾기는 **개인 전용**이다. 공유 개념이 없다 | 必 |
| FR-9.6 | 템플릿을 고르면 블록이 **샘플 값과 함께** 캔버스에 얹힌다 | 必 |

> 코드 상수로 두지 않는 이유 — 모듈이 늘어나면 템플릿 조합이 같이 늘고,
> 담당자가 «자주 쓰는 구성» 을 스스로 만드는 게 이 기능의 본질이다. 배포 없이 늘어야 한다.

### FR-10 L2 — MCP

전체 설계는 [mcp.md](./mcp.md).

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-10.1 | MD 자동화를 **원격 MCP 서버**로 노출한다 (어드민과 같은 앱) | 必 |
| FR-10.2 | 모듈이 100개가 돼도 고를 수 있게 **검색·추천 도구**를 준다 | 必 |
| FR-10.3 | 쓰기 도구는 **draft 만** 만든다. 발행·삭제 도구를 만들지 않는다 | 必 |
| FR-10.4 | 모든 쓰기 도구는 **캔버스 편집 URL** 을 돌려준다 | 必 |
| FR-10.5 | 서버가 캔버스와 **동일한 코드**로 검증한다 | 必 |

### FR-8 성과 측정

담당자가 자유롭게 만들 수 있게 해도, **잘 만들었는지 판단할 근거가 없으면 개선으로 이어지지 않는다.**
도구를 만드는 것과 같은 비중으로 다뤄야 한다 — 뒤에 붙이면 영영 안 붙는다.

| ID | 요구사항 | 우선 |
|---|---|---|
| FR-8.1 | 발행된 MD 별 **조회수**를 센다 | 必 |
| FR-8.2 | `cta` / `hotel-card-list` 의 **클릭수**를 블록 단위로 센다 | 必 |
| FR-8.3 | 어드민 MD 목록에서 조회수·클릭수를 본다 | 必 |
| FR-8.4 | 블록 **종류별** 클릭률을 본다 — 어떤 모듈이 실제로 일하는지 | 有 |
| FR-8.5 | 템플릿별 성과 비교 | 無 (v2) |

> FR-8.2 가 블록 «단위» 인 게 중요하다. 페이지 단위로만 세면 «이미지 12장 중 어느 것이 눌렸나» 를 모르고,
> 그러면 모듈을 늘릴지 줄일지 판단할 근거가 안 생긴다.

## 6. 수용 기준

기능이 «됐다» 를 판정하는 문장. 이게 없으면 어디까지 만들지 정할 수 없다.

**AC-1 (G2 · 관문)**
실사 표본 7건 중 **3건**(6355 브랜드 위크 · 6267 스페인 · 야놀자 허브)을
v1 모듈 6종만으로 **블록 순서와 종류가 같게** 재현한다.
판정: 재현 페이지의 모듈 배열이 실사 §2 의 구조와 1:1 대응한다.
→ **이걸 통과하기 전에는 모듈을 7번째로 늘리지 않는다.**

**AC-2 (G3)**
`feature-carousel` 을 추가할 때 변경 파일이 **2개**다 (신규 생성 파일 제외).
3개가 되면 설계가 샌 것이므로 되돌린다.

**AC-3 (G1)**
운영 담당자 역할로 T3(허브·특가) 템플릿을 골라 **이미지 업로드 0회**로 발행까지 간다.

**AC-4 (G4)**
요청문 20건을 넣어 페이지 JSON 스키마 **1차 통과율 ≥ 70%**, 재요청 포함 **≥ 90%**.
통과율은 재요청 전/후를 나눠 기록한다.

**AC-5 (FR-2.2)**
발행된 MD 가 있는 상태에서 모듈 컴포넌트의 여백을 바꾸면,
**재발행 없이** 그 MD 의 여백이 바뀐다.

**AC-6 (FR-2.4)**
페이지 JSON 에 존재하지 않는 모듈 타입을 넣어도 나머지 블록이 정상 렌더된다.

**AC-7 (FR-8)**
발행한 MD 를 열고 CTA 를 누르면, 어드민 목록에서 **그 블록의** 클릭수가 1 증가한다.
→ 측정은 발행(P3)과 같은 단계에서 끝낸다. 뒤로 미루지 않는다.

## 7. 비기능 요구사항

| ID | 항목 | 기준 |
|---|---|---|
| NFR-1 | 공개 페이지 LCP | 모바일 2.5s 이하 |
| NFR-2 | 접근성 | 모든 이미지 `alt` 필수(빈 문자열 허용은 장식만), 제목 계층 h1→h2 유지 |
| NFR-3 | 검색 | 본문 텍스트가 이미지가 아니라 DOM 에 있다 (FR-6.2) |
| NFR-4 | LLM 비용 | 페이지 1건 생성 1회 호출 + 재시도 최대 1회 |
| NFR-5 | 데이터 | 페이지 JSON 은 스키마 버전을 갖는다 |

## 8. 실패 모드

설계가 아니라 요구사항 단계에서 정해야 하는 것들.

| 상황 | 처리 |
|---|---|
| 렌더러가 모르는 모듈 타입 | 건너뛴다 (FR-2.4) |
| 필수 필드가 빈 값 | 저장은 막고, 이미 저장된 것은 **그 요소만 숨긴다** (페이지는 뜬다) |
| 이미지 URL 이 깨짐 | 자리를 비워 두고 레이아웃을 유지한다. 깨진 아이콘을 보이지 않는다 |
| 호텔 카드의 호텔이 사라짐 | 그 카드만 빼고 렌더. 페이지는 뜬다 |
| LLM 이 스키마를 못 맞춤 | 재요청 1회 → `draft` 저장 (FR-5.4) |
| LLM 이 없는 호텔을 지어냄 | 실호텔 목록에 없는 id 는 검증에서 탈락 (FR-5.5) |
| 노출 기간이 지난 MD 에 접근 | 404 (FR-4.3) |

## 10. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| `image` 모듈이 편해서 전부 이미지로 만든다 | 프로젝트 목적이 무효화 | AC-3 를 «이미지 0장» 으로 못 박음 + 자유도 등급(FR-1.7)으로 자유 입력을 예외로 제한 |
| 모듈을 자꾸 늘리게 된다 | G3 붕괴 | AC-1 통과 전 7번째 모듈 금지 |
| 캔버스 UI 에 시간이 다 간다 | 스키마 층이 안 나옴 | FR-3.3(폼 자동 생성)로 UI 작업량을 구조적으로 묶음 |
| 실사 표본이 여기어때에 쏠림 | 모듈 도출 편향 | 실사 §6 에 한계 명시. 표본 추가 시 재검토 |
| **AI 이미지 생성이 «글자 든 이미지»를 만든다** | 실사 F1 의 문제를 그대로 재생산 — 프로젝트 목적 무효화 | 시스템 프롬프트 고정 제약 + 사람 확인 ([mcp.md §5](./mcp.md)) |
| 모듈이 늘어도 담당자가 아는 3~4개만 쓴다 | 모듈을 100개 만든 의미가 사라짐 | `search_modules` + `suggest_template` (mcp.md §1 P1) |
| 성과 측정을 «나중에» 로 미룬다 | 모듈을 늘릴지 줄일지 판단 못 함 | AC-7 을 발행 단계(P3)에 묶음 |
